# 通信方式設計

本書は、LocalGitLabGateway における Public Gateway Service と Private Bridge Agent の通信方式を定義する仕様書である。

## 1. 目的

<!-- sec_id: sec_lgg_comm_001 -->

本書は、LocalGitLabGateway における Public Gateway Service と Private Bridge Agent の通信方式を定義する。

## 2. 前提条件

<!-- sec_id: sec_lgg_comm_002 -->

- Public Gateway Host と Private GitLab Host のサーバー費用以外は無償であること
- 長期運用の安定性を優先すること
- GitLab 本体をインターネットへ直接公開しないこと
- ChatGPT からの操作入口は Public Gateway Service に限定すること
- GitLab 認証情報は Private GitLab Host 側にのみ保持すること
- Public Gateway Host 側に GitLab Personal Access Token を保存しないこと

## 3. 採用方式

<!-- sec_id: sec_lgg_comm_003 -->

LocalGitLabGateway の初期採用方式は、以下とする。

```text
ChatGPT
  ↓ HTTPS
Public Gateway Service
  ⇅ Reverse WebSocket（FW内から接続開始、利用時のみ有効）
Private Bridge Agent
  ↓ GitLab REST API v4
Managed GitLab
```

## 4. 採用理由

<!-- sec_id: sec_lgg_comm_004 -->

| 観点 | 評価 |
| --- | --- |
| 無償性 | WebSocket、FastAPI、nginx、systemd、SQLite は無償で利用できる構成にできる |
| 安定性 | 内部側から WSS 接続を開始し、利用時のみ維持する |
| セキュリティ | GitLab を外部公開せず、Public Gateway Service から Private Bridge Agent への到達経路を 認証済みトンネル内に限定できる |
| 実装容易性 | Public Gateway Service と Private Bridge Agent を外部APIと内部APIの契約を維持し、トンネルで要求と応答を中継できる |
| 運用容易性 | Linux の systemd、journalctl、nginx と組み合わせて管理できる |

## 5. 構成要素

<!-- sec_id: sec_lgg_comm_005 -->

### 5.1 Public Gateway Host

Public Gateway Host は、インターネットから HTTPS で到達可能な Linux サーバーである。

Public Gateway Host では、以下を稼働させる。

- nginx
- Public Gateway Service
- Reverse WebSocket 接続管理
- systemd unit
- 監査ログ出力機構

### 5.2 Public Gateway Service

Public Gateway Service は、ChatGPT からの要求を受け付ける公開側 API サービスである。

Public Gateway Service は、以下を担当する。

- ChatGPT からの HTTPS 要求受付
- API Key 認証
- 要求スキーマ検証
- 操作 allowlist 検証
- request_id 採番と内部APIへの同一IDの伝播
- 監査ログ記録
- Private Bridge Agent への転送
- Private Bridge Agent からの応答整形（公開API仕様に従う正規化形式）

### 5.3 Private GitLab Host

Private GitLab Host は、ファイアウォール内部に配置された Linux サーバーである。

Private GitLab Host では、以下を稼働させる。

- Managed GitLab
- Private Bridge Agent
- WireGuard peer
- systemd unit

### 5.4 Private Bridge Agent

Private Bridge Agent は、Managed GitLab への操作を代理実行する内部側エージェントである。

Private Bridge Agent は、以下を担当する。

- Public Gateway Service からの認証済みトンネル経由の要求受付
- 内部 Bearer 認証とトンネル接続認証
- GitLab REST API v4 呼び出し
- GitLab 認証情報の内部保持
- GitLab 応答の正規化と Public Gateway から渡された request_id の維持
- 実行結果返却

## 6. 通信経路

<!-- sec_id: sec_lgg_comm_006 -->

### 6.1 ChatGPT から Public Gateway Service

| 項目 | 方針 |
| --- | --- |
| 通信方式 | HTTPS |
| 認証 | `Authorization: Bearer <API_KEY>` |
| 公開範囲 | インターネット公開 |
| 終端 | nginx |
| アプリケーション | FastAPI |

### 6.2 Public Gateway Service から Private Bridge Agent

| 項目 | 方針 |
| --- | --- |
| 通信方式 | WSS（内部側から確立する Reverse WebSocket） |
| 通信経路 | 認証済みリバーストンネル |
| 認証 | `Authorization: Bearer <INTERNAL_API_KEY>` |
| 公開範囲 | Private Bridge は FW 内限定。トンネル受入口は公開APIから分離 |
| アプリケーション | FastAPI |

### 6.3 Private Bridge Agent から Managed GitLab

| 項目 | 方針 |
| --- | --- |
| 通信方式 | HTTP または HTTPS |
| 接続先 | GitLab REST API v4 |
| 認証 | GitLab Personal Access Token |
| トークン保持場所 | Private GitLab Host のみ |

## 7. 初期ポート設計

<!-- sec_id: sec_lgg_comm_007 -->

| 用途 | ホスト | ポート例 | 公開範囲 |
| --- | --- | --- | --- |
| HTTPS | Public Gateway Host | 443/tcp | インターネット |
| Reverse WebSocket | Public Gateway Host | 443/tcp（HTTPSと経路分離） | FW内エージェントからの外向き接続 |
| Public Gateway Service | Public Gateway Host | 127.0.0.1:8080 | ローカルのみ |
| Private Bridge Agent | Private GitLab Host | 127.0.0.1:8081（例） | FW内のみ |
| Managed GitLab | Private GitLab Host | 127.0.0.1 または LAN IP | 内部のみ |

## 8. セキュリティ境界

<!-- sec_id: sec_lgg_comm_008 -->

### 8.1 Public Gateway Host に置いてよい情報

- ChatGPT から Public Gateway Service へ接続するための API Key ハッシュ
- 操作 allowlist
- 監査ログ
- トンネル接続の識別情報（秘密鍵・内部トークンは除く）

### 8.2 Public Gateway Host に置いてはならない情報

- GitLab Personal Access Token
- GitLab 管理者認証情報
- GitLab ユーザーパスワード
- CI/CD secret
- Private GitLab Host の不要な内部情報

### 8.3 Private GitLab Host に置く情報

- GitLab Personal Access Token
- Managed GitLab URL
- Private Bridge Agent 内部認証情報
- Public Gateway Service からの許可情報

## 9. 初期実装方針

<!-- sec_id: sec_lgg_comm_009 -->

### 9.1 Public Gateway Service

初期実装では、以下の API を提供する。

- `GET /health`
- `GET /api/v1/projects`
- `GET /api/v1/projects/{project_id}/branches`
- `GET /api/v1/projects/{project_id}/files/{file_path}`
- `POST /api/v1/projects/{project_id}/files/{file_path}`
- `PUT /api/v1/projects/{project_id}/files/{file_path}`
- `POST /api/v1/projects/{project_id}/merge-requests`
- `POST /api/v1/projects/{project_id}/issues`

### 9.2 Private Bridge Agent

初期実装では、`/internal/api/v1/projects` を基点とする内部 API を提供し、GitLab REST API v4 へ変換する。各操作のパスは「Private Bridge Agent API仕様」に従う。

## 10. トンネルの運用と障害時動作

<!-- sec_id: sec_lgg_comm_010 -->

- トンネルは ChatGPT 利用時に FW 内の管理操作で有効化し、利用終了時に無効化する。
- 有効化中に切断された場合のみ、制限付き再接続を試行する。無効化後は自動再接続しない。
- トンネル未接続時は GitLab 操作を実行せず、機密情報を含まないエラーを返す。
- 公開APIの Bearer 認証と、WSS 接続時のエージェント認証は別々に検証する。
- トンネル受入口は公開APIとルート・権限を分離し、認証されていない接続を拒否する。
- 要求・応答の対応付けには同一 request_id を使用し、タイムアウトと切断時に未完了要求を安全に終了する。
- 正確なトンネル認証方式、再接続間隔、タイムアウト、同時接続数は詳細設計で確定する。

## 10.1 フォールバック方針

<!-- sec_id: sec_lgg_comm_010 -->

初期方式は Reverse WebSocket とする。トンネル停止中は GitLab 操作を拒否し、公開APIから内部接続を自動起動しない。代替通信方式の採用は別途決定する。

## 11. 除外方式

<!-- sec_id: sec_lgg_comm_011 -->

### 11.1 Tailscale

Tailscale は構築容易性が高いが、外部サービス依存があるため初期採用しない。

### 11.2 商用トンネルサービス

Cloudflare Tunnel などの商用または外部SaaS依存の方式は、サーバー費用以外を無償とする条件に対して将来制約が発生する可能性があるため初期採用しない。

### 11.3 SSH Reverse Tunnel

SSH Reverse Tunnel は安定性が高いが、APIサービス間通信としての責務分離が曖昧になりやすいため初期採用しない。

## 12. 決定事項

<!-- sec_id: sec_lgg_comm_012 -->

- 初期通信方式は HTTPS 公開API + Reverse WebSocket（WSS）とする
- ChatGPT からの入口は Public Gateway Service の HTTPS API に限定する
- Private Bridge Agent は FW 内からのみ到達可能とし、FW内エージェントが外部への接続を開始する
- GitLab Personal Access Token は Private GitLab Host にのみ保存する
- Public Gateway Host は GitLab 認証情報を保持しない
