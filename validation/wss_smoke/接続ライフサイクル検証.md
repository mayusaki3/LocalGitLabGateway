# WSSトンネル運用・接続ライフサイクル検証

## 対象

- リポジトリ: `mayusaki3/LocalGitLabGateway`、`develop`
- Public Gateway / Private Bridge / 手動起動するWSS Worker
- Windowsローカル結合検証。Ubuntu Serverでの本番検証は別途実施する。

## 現行実装で確認した仕様

1. Workerはコマンド実行により手動起動する。起動状態を永続化する自動有効化フラグはない。
2. Workerは外向きに `wss://` へ接続し、認証トークンと `lgg-tunnel.v1` サブプロトコルを指定する。
3. 接続障害時は再接続を試みる。待機時間は1、2、4、8、16、30秒（上限30秒）。
4. 接続確立後は再試行回数をリセットする。
5. WSS切断時は処理中の要求タスクをキャンセルする。
6. Worker内の同時処理上限は16件。上限到達時は空き待ちする。
7. Worker停止により再接続処理も停止する。

**注意:** ChatGPTの会話・利用セッション終了を検出してWorkerを自動停止する機能は、このWorkerにはない。利用終了時は運用者がWorkerを停止する。ブラウザやChatGPTを閉じるだけではWorker停止を保証しない。

## 検証環境

| 構成 | ローカルアドレス |
| --- | --- |
| Mock GitLab | `http://127.0.0.1:8090` |
| Private Bridge | `http://127.0.0.1:8081` |
| Public Gateway | `https://localhost:8443` |
| Worker WSS | `wss://localhost:8443/internal/tunnel/v1` |

WindowsのローカルHTTPS検証にはmkcert CAを使用する。PythonのHTTPクライアントで `CERTIFICATE_VERIFY_FAILED` が出る場合は `$env:SSL_CERT_FILE = "$env:LOCALAPPDATA\mkcert\rootCA.pem"` を設定し、証明書検証を有効にしたまま再試行する。証明書検証の無効化は標準手順にしない。

## 運用手順

### 利用開始

1. Public Gateway、Private Bridge、GitLabの稼働と設定を確認する。
2. 作業を許可された運用者がWorkerを**手動起動**する。
3. Public APIの正常応答を確認してからChatGPT等のクライアントによる操作を開始する。

### 利用終了

1. 新しいAPI要求を停止する。
2. 処理中の要求が完了したことを確認する。強制停止した場合は未完了要求の失敗を想定する。
3. WorkerのPowerShellで `Ctrl+C` によりプロセスを停止する。
4. Workerが再起動されていないこと、Public APIがトンネル未接続として応答することを確認する。

### 障害発生時

- **Public Gateway停止:** Workerは接続を失い、再接続待機へ移る。Gateway復旧後に自動再接続することを確認する。
- **Private Bridge停止:** WSSは残っていても内部APIが利用できず、対象要求は502 `private_bridge_unavailable` となる。Bridge復旧後に再試行する。
- **GitLab停止:** BridgeからのGitLab呼び出しが失敗し、対象要求は502 `gitlab_unavailable` となる。GitLab復旧後に再試行する。
- **Worker停止:** Public APIはトンネル未接続の503 `tunnel_unavailable` を返す。利用再開は運用者の手動起動による。

## 運用上の注意

- WorkerをOS起動時に自動起動する設定、永続的な再起動サービス化は、手動利用開始という運用方針に反するため、明示的な仕様変更なしに導入しない。
- 公開側の認証、内部APIの認証、トンネルトークンは別の資格情報として扱う。
- ログや検証結果に実トークンを貼り付けない。
